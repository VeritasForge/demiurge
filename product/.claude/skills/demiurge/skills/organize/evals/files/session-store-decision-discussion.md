# 대화 기록: 세션 저장소 선택 — Redis vs PostgreSQL
> 아래는 사용자와 AI 어시스턴트의 실제 대화 기록이다. 턴 순서대로 기록됨.

**User:**
로그인 세션 저장소 어디에 둘지 고민 중이야. 지금은 앱 프로세스 메모리에 들고 있어서 배포할 때마다 전부 로그아웃되거든. Redis를 붙일지, 그냥 PostgreSQL 테이블에 넣을지 상의 좀 하자.
우리 상황 먼저 말하면 — 우리는 개발자 3명, 인프라 월 예산 50달러, DAU 약 2,000명, 지금은 AWS Lightsail 인스턴스 하나에 앱과 PostgreSQL이 같이 돌고 있어.

---

**Assistant:**
상황 공유 고마워요. 3명·월 50달러·DAU 2,000·Lightsail 한 대면 "정석이 뭐냐"보다 "운영 부담을 어디까지 감당할 수 있냐"가 더 중요한 조건이라고 봐요.

먼저 세션 저장소가 뭘 해줘야 하는지부터 짚고 갈게요. 필요한 성질은 크게 세 가지예요.
- 조회가 빨라야 해요. 거의 모든 요청마다 세션을 읽으니까, 여기가 느리면 전체 응답이 느려져요.
- 만료가 자동이어야 해요. 세션은 수명이 있는 데이터라 일정 시간 지나면 사라져야 하고, 그걸 앱 코드가 일일이 챙기면 놓치기 쉬워요.
- 앱 인스턴스끼리 공유돼야 해요. 지금은 한 대지만, 두 대가 되는 순간 프로세스 메모리 세션은 바로 깨져요.

이 세 가지를 기준으로 두 안을 비교하면:

| 항목 | Redis | PostgreSQL 테이블 |
|---|---|---|
| 조회 지연 | 인메모리 키 조회. 같은 머신이면 1ms 미만이 보통 | PK 조회면 같은 머신에서 보통 1ms 안팎. 체감 차이는 거의 없음 |
| 만료(TTL) | 키에 TTL 붙이면 서버가 알아서 지움 | expires_at 컬럼 + 주기적 삭제를 직접 돌려야 함 |
| 인스턴스 간 공유 | 네트워크로 붙으면 됨 | 이미 공유 DB니까 그대로 됨 |
| 운영 부담 | 프로세스 하나 더 (모니터링·메모리·재시작 정책) | 새 컴포넌트 없음. 테이블 하나 추가 |
| 비용 | 같은 머신에 올리면 0. 별도 노드로 빼면 추가 | 0 |
| 장애 시 영향 | Redis 죽으면 세션 전부 소실 → 전원 로그아웃 | DB 죽으면 어차피 앱 전체가 멈춤 (세션만의 문제가 아님) |
| 성능 상한 | Redis는 단일 스레드라 동시 접속 1만 개 정도가 한계예요. DAU 2,000이면 한참 여유 | 커넥션 풀 크기와 DB 부하에 달림 |

한 줄로 하면 Redis는 "세션에 딱 맞는 도구를 하나 더 들이는 것", PostgreSQL은 "이미 있는 걸 조금 덜 맞게 쓰는 것"이에요. 어느 쪽이 나은지는 팀이 운영 컴포넌트를 하나 더 감당할 수 있느냐에 달려 있어서, 지금 단계에선 둘 다 열어두고 보는 게 맞을 것 같아요.

---

**User:**
Lightsail 한 대에서 실제로 어떻게 배치돼? 지금 2GB짜리 쓰고 있는데 메모리 걱정도 좀 있고. Redis 띄운다면 설정도 같이 보여줘.

---

**Assistant:**
두 안을 지금 구성 위에 얹으면 이렇게 돼요.

A안 — Redis를 같은 머신에 추가:

```
┌──────────────────── Lightsail (2GB) ─────────────────────┐
│                                                          │
│   브라우저 ──▶ 앱 프로세스 ──┬──▶ PostgreSQL (업무 데이터)  │
│                            │                             │
│                            └──▶ Redis (세션만)            │
│                                 :6379, loopback          │
└──────────────────────────────────────────────────────────┘
```

B안 — PostgreSQL 안에 sessions 테이블:

```
┌──────────────────── Lightsail (2GB) ─────────────────────┐
│                                                          │
│   브라우저 ──▶ 앱 프로세스 ──▶ PostgreSQL                  │
│                                ├─ users, orders, ...     │
│                                └─ sessions  ◀ 새 테이블   │
└──────────────────────────────────────────────────────────┘
```

메모리는 크게 걱정 안 해도 돼요. DAU 2,000이고 세션 하나를 1KB 정도로 잡으면, 동시에 살아있는 세션이 2만 개여도 20MB 남짓이에요. Redis 프로세스 자체 오버헤드까지 합쳐도 2GB 중 100MB 안쪽으로 묶을 수 있어요.

A안으로 간다면 compose 조각은 이 정도로 시작하면 돼요:

```yaml
services:
  redis:
    image: redis:7-alpine
    command: >
      redis-server
      --maxmemory 128mb
      --maxmemory-policy allkeys-lru
      --save ""
      --appendonly no
    ports:
      - "127.0.0.1:6379:6379"
    restart: unless-stopped
```

포인트만 짚으면:
- `maxmemory 128mb`: 상한을 안 두면 Redis가 메모리를 계속 먹다가 앱이나 PostgreSQL을 밀어낼 수 있어요. 세션은 작으니 128MB면 넉넉해요.
- `maxmemory-policy allkeys-lru`: 상한에 닿으면 가장 오래 안 쓴 키부터 지워요. 세션 저장소에선 "오래 안 들어온 사람이 먼저 로그아웃"이라 받아들일 만한 정책이에요.
- `--save ""`, `--appendonly no`: RDB랑 AOF를 둘 다 끈 거예요. 세션은 날아가도 다시 로그인하면 되는 데이터라 디스크 쓰기를 아낀 건데, 켜고 싶으면 나중에 따로 보죠.
- 포트는 127.0.0.1에만 바인딩해서 외부에서 못 붙게 했어요. Redis는 기본 설정에 비밀번호가 없어서 이게 중요해요.

B안은 설정이랄 게 없고 테이블 하나 만들면 끝이에요. 대신 만료 정리를 직접 해야 하는데 그건 뒤에서 얘기해요.

---

**User:**
Redis 죽으면 진짜 다 로그아웃되는 거지? 그거 좀 무서운데. PostgreSQL 안은 그 문제가 없는 거야?

---

**Assistant:**
네, 위 설정대로면 Redis 프로세스가 죽는 순간 세션이 전부 사라지고, 사용자 전원이 다음 요청에서 로그아웃 상태가 돼요. 실제로 겪을 상황을 나열하면:

- OOM으로 Redis만 죽음 → 앱은 멀쩡한데 모두 로그아웃. 사용자 입장에선 "갑자기 튕겼다".
- 머신 재부팅 → `restart: unless-stopped`로 Redis는 다시 뜨지만 빈 상태로 뜸. 역시 전원 로그아웃.
- Redis 버전 올리려고 재시작 → 같은 결과. 배포 창을 잡아야 함.

완화 방법은 있어요. 위에서 끈 RDB나 AOF를 켜면 재시작 후에 상당 부분 복구되긴 해요. 다만 완전히 같은 상태로 돌아오는 건 아니고 디스크 쓰기가 생기니, 그건 별도로 따져봐야 해요.

PostgreSQL 안이면 "세션만 따로 죽는" 시나리오 자체가 없어요. 세션이 업무 데이터랑 같은 DB에 있으니까:

- DB가 살아있으면 세션도 살아있음. 앱 재배포·재시작해도 로그인 유지.
- DB가 죽으면 세션도 못 읽지만, 그땐 어차피 서비스 전체가 안 되는 상태라 "세션 때문에" 추가로 나빠지는 건 없음.

즉 B안은 장애 지점을 하나 안 늘리는 대신, 세션 읽기·쓰기 부하를 업무 DB가 같이 받는 구조예요. DAU 2,000이면 그 부하는 미미하지만, 요청마다 세션 갱신(마지막 활동 시각 같은 거)을 UPDATE로 하면 dead tuple이 쌓여서 autovacuum이 자주 돌긴 해요. 이건 갱신 빈도를 줄이는 걸로(예: 5분에 한 번만 갱신) 대부분 해결돼요.

---

**User:**
잠깐, 아까 표에서 Redis가 단일 스레드라 동시 접속 1만이 한계라고 했잖아. 그거 진짜야? 우리랑은 상관없는 숫자긴 한데 어디서 들은 거랑 달라서.

---

**Assistant:**
정정할게요 — 아까 표현이 틀렸어요.

Redis 명령 실행은 단일 스레드지만 I/O 멀티플렉싱으로 단일 인스턴스에서 초당 10만 건 이상 처리하는 게 일반적이고, 접속 수 상한은 maxclients 설정(기본 10000)과 OS 파일 디스크립터 한도의 문제이지 스레드 모델의 한계가 아니에요.

제가 "1만"이라고 한 건 maxclients 기본값을 스레드 모델의 한계인 것처럼 섞어 말한 거예요. 둘은 별개예요:
- 스레드 모델: 명령은 하나씩 순서대로 실행되지만, 각 명령이 마이크로초 단위라 처리량 자체는 매우 높음.
- 접속 수: `maxclients`를 올리고 `ulimit -n`을 맞추면 1만을 넘길 수 있음. 다만 우리 규모에선 건드릴 일이 없음.

표의 "성능 상한" 행은 "Redis: 우리 규모에선 병목 아님"으로 읽어주시면 돼요. 결론 자체(DAU 2,000이면 여유)는 그대로예요.

---

**User:**
오케이. 그럼 PostgreSQL 쪽으로 돌아가서, PostgreSQL에 세션 두면 만료된 세션 정리는 어떻게 해? Redis는 TTL이 알아서 해주잖아.

---

**Assistant:**
expires_at 컬럼을 두고 주기적으로 DELETE 하면 돼요. 스케줄은 앱 쪽 크론이나 pg_cron 같은 걸 쓸 수도 있고요. 조회할 때 만료 시각이 지난 세션은 걸러내도록만 해두면, 아직 안 지워진 만료 세션이 살아있는 것처럼 보이는 일은 없어요.

---

**User:**
인덱스는 어떻게 잡아야 해? session_id 말고 expires_at에도 걸어야 하는 거지?

---

**Assistant:**
네, 둘 다요. 테이블은 이 정도로 잡으면 돼요:

```sql
CREATE TABLE sessions (
  session_id  text        PRIMARY KEY,
  user_id     bigint      NOT NULL,
  data        jsonb       NOT NULL DEFAULT '{}',
  expires_at  timestamptz NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX sessions_expires_at_idx ON sessions (expires_at);
```

- `session_id`는 PRIMARY KEY라서 B-tree 인덱스가 자동으로 생겨요. 요청마다 도는 "쿠키 값으로 세션 찾기"가 이걸 타요.
- `expires_at` 인덱스는 정리 작업용이에요. 이게 없으면 만료 삭제가 매번 테이블 전체를 훑어요. 세션이 몇만 건이면 지금은 티가 안 나도, 인덱스 하나로 끝나는 일이라 처음부터 걸어두는 게 나아요.
- `user_id` 인덱스는 "이 사용자의 모든 기기 로그아웃" 같은 기능이 생기면 그때 추가해도 돼요.

여기까지 오면 아까 말한 세션 저장소의 세 가지 성질을 두 안이 각각 어떻게 채우는지 한 표로 볼 수 있어요:

| 필요한 성질 | 왜 필요한가 | Redis | PostgreSQL |
|---|---|---|---|
| 빠른 조회 | 거의 모든 요청이 세션을 먼저 읽음 | 인메모리 키 조회 | session_id PK 인덱스 조회 |
| TTL 만료 | 세션은 수명이 있는 데이터. 앱이 챙기면 놓침 | 키 TTL로 서버가 자동 삭제 | expires_at 컬럼 + 인덱스 + 주기 삭제 (직접 구성) |
| 인스턴스 간 공유 | 앱이 2대가 되는 순간 프로세스 메모리는 깨짐 | 네트워크로 접속 | 이미 공유 DB |

Redis는 세 가지가 전부 기본 기능이고, PostgreSQL은 두 번째 줄을 직접 만들어야 한다는 게 핵심 차이예요.

**User:**
나중에 앱 인스턴스가 2대 이상 되면 두 안이 어떻게 달라져? 지금 결정이 그때 발목 잡을지 궁금해.

---

**Assistant:**
2대가 되는 순간 "세션 저장소가 두 앱에서 모두 닿는 곳에 있어야 한다"는 조건이 생겨요. 지금은 앱·DB·(Redis)가 한 머신이라 loopback으로 끝났는데, 그게 깨지는 거예요.

```
        ┌─────────────┐    ┌─────────────┐
        │ 앱 인스턴스 1 │    │ 앱 인스턴스 2 │
        └──────┬──────┘    └──────┬──────┘
               │                  │
               └────────┬─────────┘
                        ▼
              ┌───────────────────┐
              │ 세션 저장소         │  ← 두 앱이 같이 봐야 함
              │ (Redis 또는 PG)    │     네트워크 너머
              └───────────────────┘
```

A안(Redis)에서 달라지는 것:
- Redis를 두 앱이 접근 가능한 곳으로 옮겨야 해요. 기존 머신에 그대로 두고 두 번째 앱이 사설 네트워크로 붙거나, 별도 노드로 빼거나.
- 옮기는 순간 `127.0.0.1` 바인딩을 풀어야 하니 비밀번호(`requirepass`)와 방화벽 설정이 필수가 돼요.
- 별도 노드로 빼면 그게 비용이에요. 월 50달러 예산 안에서 노드를 하나 더 쓸 수 있는지 그때 다시 계산해야 해요.

B안(PostgreSQL)에서 달라지는 것:
- 세션 테이블은 이미 공유 DB에 있으니 세션 때문에 새로 할 일은 없어요.
- 대신 PostgreSQL 자체를 두 앱이 접근할 수 있게 해야 하는데, 이건 세션과 무관하게 앱을 2대로 늘리면 어차피 해야 하는 일이에요.

정리하면 2대 확장 자체는 어느 안이든 막히지 않아요. 차이는 그 시점에 "손볼 컴포넌트가 하나(PG)냐 둘(PG+Redis)이냐"예요. 반대로 Redis를 이미 분리해뒀다면 세션 부하가 DB에서 완전히 빠져 있다는 이점이 그때 생기고요.

**Assistant:**
