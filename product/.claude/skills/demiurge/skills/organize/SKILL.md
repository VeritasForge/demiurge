# 대화 내용 구조화 정리

대화에서 논의한 내용을 **원문을 최대한 보존**하면서 구조화하고, 빠진 부분을 **보강**하여 정리한다.

```
Parse the user's input from: $ARGUMENTS
```

## Step 0: 모드 감지 (필수 — 건너뛰지 마라)

`$ARGUMENTS`에서 **파일 경로**를 감지한다.

**감지 규칙** — 다음 중 하나라도 해당하면 파일 경로로 판단한다:
- `@파일명` 형태 (예: `@02-aws-iam-group-concept-explainer.md`)
- `.md`로 끝나는 문자열 (예: `02-aws-iam-group-concept-explainer.md`)
- 슬래시를 포함하는 경로 (예: `wiki/security/02-aws-iam-group.md`)

**판별 순서:**
1. 파일 경로를 감지했는가?
   - No → **생성 모드** (Step C1~C5)로 진행
   - Yes → 2번으로
2. 해당 파일이 존재하는가? (Read 도구로 확인)
   - No → **생성 모드** (Step C1~C5)로 진행
   - Yes → **병합 모드** (Step M1~M6)로 진행. **Step C1~C5는 무시하라.**

⚠️ **병합 모드가 감지되면 생성 모드의 어떤 Step도 참조하지 마라.** 특히 Step C5의 "직접 출력 (파일 저장 없음)"은 병합 모드에 적용되지 않는다.

## 생성 모드 (Create Mode)

대화를 **씨앗**으로 삼아, 그 문서 하나만 읽어도 주제를 완전히 이해할 수 있는 **독립 참고 문서**를 만들어 **화면에 출력**한다.

대화 기록을 그대로 재배열한 문서는 그 대화에 참여한 사람만 이해할 수 있다. 목표 독자는 대화를 본 적 없는 사람(한 달 뒤의 사용자 본인 포함)이다. 그래서 원문을 보존하는 것만으로는 부족하고, 대화가 건너뛴 부분을 채우고 예시를 더해야 한다.

### Step C1: 대상 식별

- `$ARGUMENTS`에 주제 힌트가 있으면: 해당 주제의 대화 내용만 추출
- 주제 힌트가 없으면: 가장 최근에 깊이 논의된 주제 전체를 대상으로 함

### Step C2: 목차 설계 (본문을 쓰기 전에)

문장을 옮기기 전에 목차부터 만든다. 목차 없이 대화를 옮기면 대화 순서(시간순)가 그대로 문서 순서가 되어 논리가 끊긴다.

1. 대화에서 다룬 주제를 모두 뽑아 **논리순**으로 배치한다: 배경 지식 → 핵심 개념 → 동작 원리 → 실전 적용 → 주의점 → 정리.
2. **사용자의 질문 목록을 다시 읽는다.** 질문은 "이 독자가 어디서 막혔는가"의 기록이다. 질문이 나온 지점은 다른 독자도 막힐 지점이므로 그 부분을 별도 절로 두텁게 잡는다. 짧게 답하고 넘어간 질문이 있으면 그 절이 보강 1순위다.
3. 대화가 다루지 않았지만 독자가 이해하려면 필요한 주제(전제 개념, 지나가듯 언급만 된 용어)를 목차에 추가한다.
4. **각 개념은 목차에서 자리를 하나만 갖는다.** 배경 절에서 핵심 개념을 미리 풀어 쓰고 뒤에서 또 설명하는 구조가 중복의 가장 흔한 원인이다. 배경 절은 "왜 이 주제가 필요한가"까지만 다루고, 개념 설명은 그 개념의 절에 몰아 둔다.
5. 완성된 목차를 문서 서두에 넣는다.

### Step C3: 원문 보존 — 줄이지 마라

1. **원문 유지**: 대화의 설명·비유·코드·표·다이어그램은 그대로 옮긴다. 요약으로 대체하지 않는다. 정리 과정에서 분량이 줄었다면 무언가를 잃은 것이다. 원문의 설명은 대화 당시 독자의 질문에 맞춰 나온 것이라 요약본보다 이해에 훨씬 효과적이다.
2. **중복 병합**: 같은 내용이 반복되면 가장 완성도 높은 버전을 채택하되, 다른 버전에만 있던 세부·비유는 합쳐 넣는다. 병합한 설명은 **한 절에만** 둔다. 도입부나 정리 표에서 다시 필요하면 한 줄 요약과 절 번호 참조로 대신한다. 같은 설명이 두 곳에 있으면 독자는 어느 쪽이 정본인지 헷갈리고, 나중에 한쪽만 고쳐져 문서가 어긋난다.
3. **정정 반영**: 후속 대화에서 정정된 내용은 **정정된 버전만** 남긴다. 잘못된 버전은 흔적 없이 지운다.
4. **맥락 보존**: 질문의 맥락이 답변 이해에 필요하면 자연스럽게 녹여넣는다. 단 "앞서 질문하신", "대화에서 말씀드린" 같은 대화 참조 표현은 쓰지 않는다. 독자는 그 대화를 본 적이 없다.

### Step C4: 보강 — 조합에서 멈추지 마라

보강의 기준은 하나다: **"이 문서만 읽는 사람이 막히는 지점이 남아 있는가?"**

1. **빠진 개념 채우기**: 목차 설계에서 찾은 빈 곳(언급만 된 용어, 얕게 답한 질문, 전제 지식)을 본문 수준으로 써넣는다.
2. **예시 풍부화**: 추상적 설명마다 구체 예시를 붙인다. 개념 하나에 예시 하나로는 부족하다. 정상 케이스와 실패·예외 케이스를 함께 보이면 경계가 드러난다.
3. **실행 가능한 코드 예제**: 대화의 도메인에서 실무자가 실제로 쓰는 도구로 쓴다. 대화에 이미 등장한 도구가 있으면 그것을 따르고(예: Terraform이 나왔으면 Terraform), 없으면 도메인 표준을 쓴다(클라우드 인프라 → Terraform, DB → SQL, 컨테이너 → YAML manifest, API → 요청/응답 예시). 조각이 아니라 그대로 실행되는 단위로.
4. **시각화**: 구성 요소 간 관계, 요청·응답 흐름, 상태 전이, 시간에 따른 변화는 글 대신 ASCII 다이어그램으로 그린다. 특히 셋 이상이 얽힌 흐름(A→B→C)은 글로만 풀면 독자가 구간을 헷갈린다. 비교는 표로.
5. **보강하며 들여온 용어도 첫 등장에 정의한다.** 보강은 독자의 빈칸을 메우는 일인데, 새 용어(약어, API·옵션 이름, 프로토콜 이름)를 정의 없이 쓰면 빈칸을 옮긴 것에 불과하다. 본문에서 한 줄로 풀거나 용어집 절에 넣는다. 대화에서 언급만 된 용어와 같은 기준이다.

**보강의 한계 — 지어내지 말 것:**

- 대화에서 내려진 **결정**, 사용자의 **고유 상황·수치**(팀 규모, 예산, 트래픽, 현재 구성)는 원문 그대로 둔다. 결정이 나지 않았으면 미결 상태 그대로 둔다. 보강은 일반 지식(개념·원리·예시·공식 동작)에만 적용한다.
- 버전·수치·기본값처럼 확신이 서지 않는 사실은 단정하지 말고 "(확인 필요)"를 붙인다. 틀린 보강은 빈칸보다 나쁘다.

### Step C5: 출력

- **구조**: H1 제목 → 목차 → 본문(H2/H3, 논리순) → 정리
- **포맷**: 코드 블록에 언어 식별자, 마크다운 표, 다이어그램은 코드 블록 안에
- 구조화된 마크다운 문서를 **직접 출력** (파일 저장 없음)
- 출력 전후에 부가 설명 없이 문서 내용만 출력

## 병합 모드 (Merge Mode)

기존 파일의 **섹션 구조를 유지**하면서, 대화 내용을 각 섹션에 **자연스럽게 녹여넣는다.**

### Step M1: 원문 분석

대상 파일을 **Read 도구**로 읽어서 **섹션 구조**를 파악한다 (H1, H2, H3 계층, frontmatter, Sources 등).

### Step M2: 대화 내용 추출

전체 대화에서 병합할 내용을 스캔하여 추출한다:
- Q&A 답변 내용
- 논의/토론에서 나온 보충 설명
- 정정된 정보 (원문의 부정확한 부분)
- 새로운 근거/출처

**대화 내용과 대상 파일의 관련성 판별:**
- 대화 내용이 대상 파일의 주제와 **직접 관련**있으면 → 해당 내용을 추출하여 병합
- 대화 내용이 대상 파일과 **관련이 적으면** → 사용자에게 알린다: "대화 내용 중 [파일명]과 관련된 항목이 N개입니다. 병합을 진행할까요?"
- 관련 내용이 **전혀 없으면** → 사용자에게 알린다: "현재 대화에서 [파일명]에 병합할 내용을 찾지 못했습니다."

### Step M3: 섹션 매핑

추출된 내용을 원문의 **어떤 섹션에 배치할지** 매핑 테이블을 작성하여 화면에 출력한다.

```
매핑 테이블 예시:
Q1 (Principal 설명)     → 2️⃣ 핵심 개념 — 핵심 규칙 #3 보충
Q3 (Deny 우선)          → 3️⃣ 아키텍처 — 권한 평가 보충
Q6 (Group Principal 에러) → 7️⃣ 주의점 — 흔한 실수 #5 보충
```

### Step M4: 병합 결과 미리보기

병합된 **전체 문서를 화면에 출력**한다. 이 단계에서는 파일을 수정하지 않는다.

**병합 원칙:**

1. **원문 구조 보존**: 기존 섹션 순서, 다이어그램, 표, 코드 블록은 그대로 유지
2. **`> 💡` blockquote로 보충**: 보충 내용은 관련 섹션의 해당 항목 바로 뒤에 `> 💡` 블록으로 삽입
3. **정정 우선**: 원문에 부정확한 부분이 대화에서 정정되었으면 원문 자체를 수정
4. **Sources 추가**: 대화에서 인용한 새 출처를 Sources 섹션에 추가
5. **메타데이터 갱신**: Research Metadata 등 문서 메타 정보도 업데이트

**하지 말 것:**
- 별도 Q&A 섹션을 만들지 않는다 — 반드시 관련 섹션에 녹여넣는다
- 원문의 기존 내용을 삭제하지 않는다 (정정된 경우만 예외)
- 원문의 섹션 순서를 변경하지 않는다

### Step M5: 사용자 확인

미리보기 출력 후 사용자에게 확인을 요청한다:

> "파일에 반영할까요?"

- 사용자가 **승인** → Step M6으로 진행
- 사용자가 **수정 요청** → 요청 사항을 반영하여 Step M4를 다시 수행
- 사용자가 **거부** → 종료 (파일 수정 없음)

### Step M6: 파일 저장 + 결과 요약

**Write 도구로 파일을 저장**하고, 어떤 섹션에 무엇이 추가/수정되었는지 간단히 요약한다.

```
예시:
✅ 파일 저장 완료: wiki/security/02-aws-iam-group-concept-explainer.md
- 2️⃣ 핵심 개념: Principal/Effect 역할 구분, AllUsers 예시 설명 추가
- 3️⃣ 아키텍처: 명시적 Deny 우선순위 상세 설명 추가
- 7️⃣ 주의점: 실수 #5 에러 메시지/Workaround 보충
- 📎 Sources: 공식 문서 3개 추가 (8→10건)
```
