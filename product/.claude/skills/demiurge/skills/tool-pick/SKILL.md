# tool-pick: 실측 수치로 개발 도구 고르기

학습 데이터만으로 도구를 추천하면 두 가지가 틀린다. 최근 등장한 후보를 모르고, "star가 많으니 인기 있다" 같은 겉보기 수치에 속는다. 이 스킬은 후보를 넓게 찾고, 공개 API에서 수치를 직접 조회하고, 비교가 성립하지 않는 수치를 걸러낸 뒤 상황별로 추천한다.

요청: `$ARGUMENTS`

## 1. 요청 해석

요청에서 세 가지를 읽는다.

| 읽을 것 | 예 | 영향 |
|---|---|---|
| 후보가 주어졌나 | "uv vs poetry" → 있음 / "빠른 Python 패키지 매니저" → 없음 | 없으면 2단계에서 후보를 찾는다 |
| 후보가 하나인가 | "zod 아직 관리돼?" | 하나면 비교 대신 **단일 점검**으로 출력한다 |
| 보안 언급이 있나 | "보안도 봐줘", "회사 보안 심사" | 있으면 스크립트에 `--security`를 붙인다 |

사용자가 말한 조건(메모리, 라이선스, 플랫폼, 언어 등)도 적어 둔다. 추천표의 축이 된다. 데스크톱 앱처럼 실행 환경이 판단에 영향을 주면 `uname -m`, 메모리 크기, 이미 설치된 도구를 확인한다.

## 2. 후보 찾기 (후보가 주어지지 않았을 때만)

1. 학습 데이터로 후보 3~5개 초안을 만든다.
2. 웹 검색 1~2회로 빠진 후보를 보강한다. 예: `"<분야> alternatives 2026"`, `"<기존 대표 도구> vs"`. 학습 이후 나온 도구를 잡는 게 목적이다.
3. 사용자 조건에 명백히 맞지 않는 후보는 이유를 한 줄 남기고 뺀다.

## 3. 수치 조회

후보마다 GitHub 레포와 패키지 이름을 정해 스크립트를 실행한다. 후보끼리는 독립적이므로 한 번에 병렬로 실행한다.

```bash
python3 <이 스킬 폴더>/scripts/fetch_metrics.py --github <owner/repo> [--brew X] [--npm X] [--pypi X] [--crate X] [--go <module>] [--security]
```

| 도구 종류 | 사용량 출처 플래그 | 무엇을 재나 |
|---|---|---|
| macOS 앱·CLI | `--brew` (formula·cask 자동 판별) | 30/90/365일 설치 수 |
| JS/TS | `--npm` | 최근 1주/1달 다운로드 |
| Python | `--pypi` | 최근 1주/1달 다운로드 |
| Rust | `--crate` | 누적, 최근 90일 다운로드 |
| Go | `--go` | 다운로드 통계가 없어서 pkg.go.dev의 "Imported by"(이 모듈을 import하는 모듈 수) |

- CLI 도구가 언어 생태계로도 배포되면(예: uv는 PyPI와 Homebrew 모두) 둘 다 조회한다.
- 출처 하나가 실패하면 그 출처에만 `error`가 남는다. 결과표에 "조회 실패"로 적고 나머지 수치로 판정한다. 특히 Go의 "Imported by"는 HTML 파싱이라 깨질 수 있다.
- `github_auth: false`면 GitHub 비인증 한도(시간당 60회, 후보 하나에 4회)에 걸릴 수 있다. 403이 나면 사용자에게 `gh auth login`을 안내한다.

라이선스나 가격이 조건에 걸리는 상용 제품은 공식 가격 페이지를 열어 개인용/업무용 조건을 확인한다.

## 4. 비교가 성립하는지 거르기

수치를 표에 넣기 전에 아래 함정을 확인한다. 이 단계가 이 스킬의 핵심이다. 걸러낸 수치는 지우지 말고 표에 남기되 왜 비교에서 뺐는지 적는다.

| 함정 | 확인 방법 | 처리 |
|---|---|---|
| 비공개 소스 앱의 레포는 이슈 트래커일 뿐이다 | 스크립트의 `warning` 필드 (릴리스 0개 + 180일 넘게 push 없음) | star·커밋을 비교에서 제외. 사용량은 brew 등으로 판단 |
| 다운로드 출처가 후보마다 다르다 | 한 후보는 npm, 다른 후보는 brew만 있는 경우 | 서로 다른 출처의 숫자를 직접 비교하지 않는다. 공통 출처가 없으면 "직접 비교 불가"로 적는다 |
| 기간이 다른 수치를 섞는다 | npm은 30일, crates는 90일, brew는 30/90/365일 | 같은 기간끼리만 비교한다 |
| Scorecard 총점은 보안 점수다 | 스크립트는 총점을 일부러 내보내지 않는다 | 유지보수 판정에는 `Maintained`·`Code-Review`만 쓴다 |
| Scorecard는 실시간이 아니다 | `scan_date` | 날짜를 함께 적는다. GitHub 실시간 수치와 어긋나면 GitHub 쪽을 우선한다 |
| 1인 프로젝트 | `top1_share_of_top30_humans`가 0.8 이상, `Code-Review`가 낮음 | "버스 팩터(한 사람이 빠지면 멈출 위험) 높음"으로 적는다 |
| 봇 커밋으로 활동이 부풀려진다 | `commits_last_90d`와 `human_commits_last_90d`의 차이 | 사람 커밋 기준으로 판단한다 |
| archived 레포 | `archived: true` | 후보에서 사실상 탈락. 이유를 적는다 |

판단할 근거가 부족한 칸은 억지로 채우지 말고 "판단 불가"로 둔다.

## 5. 출력

터미널 답변으로만 낸다. 파일은 만들지 않는다. 아래 구조를 지킨다.

```markdown
## 결론 ✅
<1~3문장: 상황별 한 줄 추천. 예: "개인 학습이면 A, 업무용이면 B">

## 📊 실측 수치 (<조회 날짜> 기준)
| 항목 | 후보1 | 후보2 | 비고 |
<star, 사용량(출처·기간 명시), 최신 릴리스, 최근 90일 사람 커밋, Maintained/Code-Review(스캔 날짜), 기여자 집중도, 라이선스>
> 수치 출처: <쓴 API 나열>

## 🔍 판단 근거
<4단계에서 걸러낸 함정과 그 이유, 유지보수 활발도 해석, 차이가 결론을 바꾸는 지점>

## 🎯 상황별 추천
| 상황 | 추천 | 이유 |
```

후보가 하나인 단일 점검이면 비교표 대신 "📊 실측 수치" 한 열과 "건강 판정"(활발 / 느려짐 / 방치 의심 / 판단 불가 중 하나와 근거)을 낸다.

용어는 처음 나올 때 괄호로 풀어 쓴다. 예: Scorecard(OpenSSF가 레포를 자동 채점한 결과), 버스 팩터.
