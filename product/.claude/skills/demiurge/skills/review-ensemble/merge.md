# 병합 규칙

SKILL.md의 Phase 5에서 읽는다. 엔진마다 등급 체계와 출력 형식이 다르므로, 비교 가능한 하나의 자로 옮긴 뒤에 합친다.

---

## 통합 발견 스키마

모든 엔진의 결과를 이 모양으로 만든다. 엔진에 프롬프트로 넘길 때도 이걸 그대로 붙인다.

```json
{
  "engine": "ce | builtin | lens:silent-failure | lens:tests | lens:types | lens:comments | lens:workflows",
  "title": "10단어 이내의 구체적인 제목",
  "severity": "P0 | P1 | P2 | P3",
  "file": "레포 루트 기준 상대 경로",
  "line": 42,
  "why_it_matters": "무엇이 깨지는지. '무엇이 잘못됐는지'가 아니라 '무엇이 깨지는지'",
  "evidence": ["파일:줄 + 원문 그대로의 코드 줄", "..."],
  "suggested_fix": "구체적인 최소 수정안 또는 null",
  "confidence": 0,
  "pre_existing": false
}
```

`confidence`는 0·25·50·75·100 중 하나만 쓴다. 소수점이나 중간값을 허용하면 엔진마다 자를 다르게 쓰게 되어 비교가 성립하지 않는다.

각 값의 뜻:

| 값 | 판정 기준 |
|----|-----------|
| 100 | 코드만 봐도 성립. 컴파일 에러, 타입 불일치, 확정적 논리 버그, 인용 가능한 규약 위반 |
| 75 | 재확인했고 정상 사용 경로에서 사용자·호출자·런타임에 영향이 간다 |
| 50 | 실재하는 문제인 건 확인했으나 지엽적이거나 실질 영향이 작다. 스타일 선호는 여기 |
| 25 | 진짜일 수도 있으나 검증하지 못했다 |
| 0 | 가벼운 검토에도 무너진다. 또는 이 변경이 만든 문제가 아니다 |

## 등급 정규화표

### 내장 code-review → 통합

내장 엔진은 `ReportFindings`로 결과를 내며 **등급 필드가 없다.** `category`와 `failure_scenario`로 판정한다.

| 원본 | → 통합 |
|------|--------|
| `verdict: CONFIRMED` | `confidence: 100` |
| `verdict: PLAUSIBLE` | `confidence: 50` |
| `verdict` 없음 | `confidence: 75` |
| `category: correctness` + `failure_scenario`가 데이터 손상·인증 우회·크래시·비밀값 유출 | `severity: P0` |
| `category: correctness` + 그 외 | `severity: P1` |
| `category: test-coverage` | `severity: P2` |
| `category: conventions` (CLAUDE.md 규칙 위반 — 인용 가능한 규칙이 있어야만 나옴) | `severity: P2` |
| `category: simplification`·`efficiency`·`reuse`·`altitude` | `severity: P3` |
| 그 외 처음 보는 category | `severity: P2` / `confidence: 50`으로 놓고 커버리지에 기록 |
| `summary` | `why_it_matters` |
| `failure_scenario` | `evidence[0]` |
| `short_summary` | `title` |

내장 엔진은 발견사항을 **심각한 것부터 정렬해서** 낸다. 위 표로 등급이 애매하게 갈리면 이 순서를 보조 근거로 쓴다 — 목록 맨 앞 것이 맨 뒤 것보다 낮은 등급으로 나왔다면 판정을 다시 본다.

**산문으로 돌아왔을 때 (자주 있는 일).** 위 표는 내장 엔진이 구조화된 발견 목록을 낼 때의 매핑이다. 그런데 그 출력 경로는 세션 설정에 따라 **없을 수 있고**, 그러면 엔진은 같은 내용을 마크다운 산문으로 낸다. 실패가 아니라 정상 대체 경로이므로 결과를 버리지 않는다.

이때는 산문에서 직접 옮긴다:

| 산문에서 | → 통합 |
|---|---|
| `파일:줄 — HIGH/MEDIUM/LOW` 류의 자체 등급 표기 | HIGH→P1, MEDIUM→P2, LOW→P3 (승격 규칙은 아래 별도) |
| 본문에 적힌 실패 시나리오 | `why_it_matters` |
| 인용된 코드 줄 | `evidence[0]` |
| **확신도 표기 없음** (산문에는 대개 없다) | `confidence: 75`. 단 지적을 성립시키는 데 필요한 사실이 **전부** 인용·확인됐으면 `100` — 사실이 둘 필요한 주장(문서가 X라 하는데 코드는 Y다)은 양쪽이 다 있어야 하고, 한쪽만 있으면 75 |
| 등급 표기가 아예 없음 | 목록 순서(심각한 것부터)로 상대 순위를 잡고 `confidence: 75`로 놓은 뒤 커버리지에 "등급 추정" 기록 |

**승격 규칙은 원 등급과 무관하다.** 발견 **자신의** 실패 시나리오가 데이터 손실·손상, 인증 우회, 되돌릴 수 없는 상태 변경이면 엔진이 뭐라고 이름 붙였든 최소 P1로 올리고, 그 피해가 실제로 확인됐으면 P0으로 올린다. 엔진마다 등급 어휘의 눈금이 다르므로 이름을 그대로 믿지 않는다.

**단, 다른 발견을 유발하기만 하는 것은 승격하지 않는다.** "이 문서가 오해를 낳아 사람이 위험한 모드를 켜게 된다"처럼 **자신은 피해를 내지 않고 다른 발견의 발생 확률만 높이는** 항목은 원 등급을 유지하고, 대신 그 발견과 묶어 관계를 명시한다. 승격 대상은 그 항목 자체가 피해를 일으킬 때다.

산문 반환을 받았다는 사실 자체를 커버리지에 한 줄 남긴다 — 등급이 매핑을 거쳤음을 나중에 감사할 수 있어야 한다.

### ce-code-review → 통합

정규화가 필요 없다. `severity`도 `confidence`도 같은 체계다. `engine: "ce"`만 붙인다.

### 전문 렌즈 에이전트 → 통합

프롬프트에서 통합 스키마를 직접 요구하므로 정규화가 필요 없다. 다만 반환값이 스키마를 벗어났으면(마크다운을 섞어 보냈다든지) 그 엔진 결과만 버리지 말고, 받은 내용에서 파일·라인·주장을 뽑아 직접 스키마로 옮긴다. 등급을 알 수 없으면 `P2` / `confidence: 50`으로 놓고 그 사실을 커버리지에 적는다.

## 중복 제거

중복 판정은 **두 경로**로 한다. 같은 위치를 지적한 경우(A)와, 같은 결함을 인과 사슬의 서로 다른 지점에서 지적한 경우(B)다. B를 빠뜨리면 교차확인이 통째로 사라진다.

### 경로 A — 같은 위치

아래를 **모두** 만족하면 합친다.

1. 파일 경로가 같다 (앞의 `./`, 워크트리 절대경로 접두사를 떼고 비교)
2. 라인 번호 차이가 3 이내
3. 주장의 핵심이 같다 — 같은 줄을 두고 서로 다른 문제를 말하는 것이면 합치지 않는다

> 3번이 판단을 요구하는 지점이다. "이 쿼리가 N+1이다"와 "이 쿼리에 인덱스가 없다"는 같은 줄이어도 다른 발견이다. 반면 "예외를 삼킨다"와 "catch 블록이 비어 있어 실패가 묻힌다"는 같은 발견이다.

### 경로 B — 다른 위치, 같은 결함

**파일이 달라도 합쳐야 하는 경우가 있다.** 하나의 결함은 보통 인과 사슬을 이루고, 엔진마다 그 사슬의 다른 지점에 앵커를 박는다 — 한 엔진은 원인이 되는 줄을, 다른 엔진은 그 결과가 드러나는 줄을 지목한다. 파일 경로만 비교하면 이 둘이 별개 발견으로 남아 **교차확인 신호가 사라지고, 같은 문제가 PR에 두 번 달린다.**

다음 세 질문에 전부 "예"면 위치가 달라도 합친다:

1. **하나의 수정으로 둘 다 해소되는가** — 제안된 수정안이 실질적으로 같은가
2. **근본 원인이 같은가** — 한쪽이 다른 쪽의 원인이거나 결과인가
3. **실패 시나리오가 같은가** — 사용자·운영자가 겪는 사건이 하나인가

> 실제 사례: 한 엔진은 `pipeline/run.py:34`(빈 산출을 반환하는 줄)을, 다른 엔진은 `app.py:47`(그 모드가 기동하게 된 줄)을 지목했다. 파일이 달라 규칙 A로는 안 잡히지만, 수정안(전 메시지를 보류로 내보내거나 기동 거부 유지)도 실패 시나리오(플래그를 켜면 메시지가 무신호로 유실)도 같으므로 하나의 발견이다. **대표 위치는 `run.py:34`** — 원인은 `app.py:47`이지만 수정이 들어갈 자리는 stub 쪽이다.

합칠 때 **대표 위치는 수정이 들어갈 쪽**으로 잡고, 나머지 위치는 `also_at` 필드에 함께 싣는다. 인라인 코멘트는 고칠 자리에 달려야 하기 때문이다 — 원인이 되는 줄과 고칠 줄이 다르면 **고칠 줄이 대표**다. 수정안이 여러 자리를 건드리면 가장 위쪽(호출 사슬의 상류) 자리를 대표로 잡는다.

### 합치지 않는 반례

원인과 결과가 **각각 독립적으로 고쳐야 하는 별개 결함**이면 합치지 않는다. 판별법: 한쪽만 고쳐도 다른 쪽이 그대로 남아 여전히 문제인가? 그렇다면 둘이다.

### 합칠 때 값 선택

| 필드 | 규칙 |
|------|------|
| `severity` | 가장 높은 것 |
| `confidence` | 가장 높은 것 |
| `title`·`why_it_matters` | 가장 구체적인 것 |
| `suggested_fix` | 실제 코드 수정안이 있는 것. 여러 개면 가장 최소한의 것 |
| `evidence` | 합집합, 최대 3개. 원문 코드 줄이 있는 것을 우선 |
| `pre_existing` | 하나라도 `false`면 `false` |
| `engines` | 합집합 (새로 생기는 필드) |
| `also_at` | 경로 B로 합친 경우, 대표 위치가 아닌 쪽의 `file:line` (새로 생기는 필드) |

**심각도는 합칠 때 근거까지 함께 본다.** 한 엔진이 다른 엔진에는 없던 사실(하류 소비자 추적, 실제 피해 범위)을 들고 왔다면, 그 근거는 낮은 쪽 엔진의 등급 판단을 무효화한다 — "가장 높은 것"을 기계적으로 고르는 게 아니라, **가장 많은 근거를 가진 판단**을 택한다. 검증자가 등급 이견을 냈더라도 그 이견이 **못 본 근거**가 있으면 이견을 기각하고 사유를 리포트에 남긴다. 엔진은 병렬로 독립 실행되므로 "먼저/나중"이라는 시간 순서는 없다 — 기준은 **그 판단이 무엇을 보고 내려졌는가**뿐이다.

**경로 B로 합친 발견의 `covering_engines`는 대표 위치 기준으로 센다.** 합집합으로 세면 실제로 한 파일만 본 엔진이 다른 파일까지 본 것으로 계산돼 계수가 부풀고, 교집합으로 세면 인과 사슬이 길수록 0에 가까워진다.

## 모순 발견 — 같은 자리에 정반대 처방

두 엔진이 **같은 줄을 지적하면서 서로를 무효화하는 수정안**을 낼 수 있다. 한쪽은 "이 배선을 테스트로 고정하라", 다른 쪽은 "이 배선을 제거하라" 같은 경우다. 둘 다 사실 판단은 맞고 처방만 반대다.

이것을 일반 발견 두 건으로 내보내면 **PR에 상충하는 지시가 나란히 달려**, 읽는 사람이 어느 쪽을 따라야 할지 알 수 없다. 자동으로 고치는 도구가 붙어 있으면 둘 중 먼저 걸린 것을 적용해 다른 하나를 조용히 무너뜨린다.

### 판정

같은 파일·라인(±3)에 걸린 두 발견의 수정안이 **동시에 적용 불가능**하면 모순으로 분류한다. 판별법: 한쪽 수정안을 적용한 뒤에도 다른 쪽 수정안이 여전히 말이 되는가? 안 되면 모순이다.

**"테스트를 추가하라 vs 코드를 고쳐라" 구도는 그 자체로 모순이 아니다.** 이 구도는 자주 나오고 양쪽으로 갈리므로, **그 테스트가 무엇을 잠그는지**로 판정한다:

| 테스트가 잠그는 것 | 판정 | 이유 |
|---|---|---|
| **특정 값·배선** (이 인자가 이 값으로 넘어간다) | 충돌 가능 — 그 값을 바꾸는 처방과 양립 불가 | 배선을 지우면 배선을 단정하는 테스트가 성립하지 않는다 |
| **관측 가능한 행동** (이 조건에서 이런 일이 일어난다) | 보통 상보 — 합친다 | 구현을 바꿔도 행동 단정은 그대로 유효하다 |

> 실제 사례 두 개가 같은 구도인데 갈렸다. `service.py:73`은 "로그가 남는지 단정"(행동) vs "인자를 필수화"(구현)라 **합쳤고**, `app.py:60`은 "클라이언트가 1회 생성되는지 단정"(배선 값) vs "그 배선을 제거"라 **모순**이었다.

### 처리

- **합치지 않는다.** 하나의 발견으로 뭉개면 어느 처방인지가 사라진다
- **일반 발견 목록에서 빼서 "결정 필요" 항목으로 승격한다.** 등급은 두 발견 중 높은 쪽을 따른다
- 항목에 **양쪽 진단·양쪽 처방·무엇을 정해야 갈리는지**를 나란히 적는다. 한쪽을 고르지 않는다 — 고르는 것은 사람 몫이다
- **자동 수정 대상에서 제외한다.** 결정이 나기 전에는 어느 쪽도 적용하지 않는다
- **계수는 계산하되 쓰지 않는다.** `engine_count`를 기록은 하되 교차확인 배지를 붙이지 않고, Phase 6 검증 게이트 대상에서도 뺀다. 두 엔진이 같은 자리를 봤다는 사실이 "여럿이 이 처방에 동의했다"로 읽히면 안 되고, 검증자에게 보내도 "어느 처방이 맞나"는 사람이 정할 문제라 답이 안 나온다. 요약의 교차확인 건수에도 넣지 않는다

> 실제 사례: `app.py:60`의 `llm=_vertex(settings)` 배선을 두고 한 엔진은 "테스트가 안 잠겨 누가 지우면 자격증명 경로가 통째로 빠진다 → 테스트로 고정하라", 다른 엔진은 "LLM을 0회 부르는 모드가 Vertex 기동 요건을 짊어진다 → `llm=None`으로 제거하라"를 냈다. 갈리는 지점은 "배선을 이관 전에 미리 걸어 둔다"는 원 설계 의도를 유지할지 여부이고, 그건 리뷰어가 아니라 저자가 정한다.

## 교차확인 계수

합친 발견마다 두 숫자를 계산한다.

**`engine_count`** — 이 발견을 지적한 서로 다른 엔진의 수.

> ⚠️ **ce-code-review는 1로 센다.** ce는 내부에서 관점 13종을 돌린 뒤 이미 자기들끼리 병합한 결과를 준다. 그 관점 수를 세면 ce 혼자 교차확인 기준을 채워버려 계수가 아무 의미도 갖지 못한다. 전문 렌즈 에이전트들은 서로 독립적으로 돌므로 각각 1로 센다.

**`covering_engines`** — 그 파일을 **실제로 본** 엔진의 수. 다음을 뺀다:
- 실패한 엔진
- 그 파일이 리뷰 범위에 안 들어간 엔진 (조건부 렌즈는 자기 신호에 해당하는 파일만 본다)

이 둘이 갈라져야 판정이 정확해진다. "둘이 봤는데 하나만 지적했다"와 "애초에 하나만 봤다"는 전혀 다른 상황인데, `engine_count`만 보면 둘 다 `1`로 똑같이 보인다.

### 소프트 버킷 항목은 계수에 넣지 않는다

엔진 중 일부는 발견 기준에 못 미친다고 판단한 항목을 별도 목록(잔여 리스크·테스트 갭 등)에 담아 낸다. 다른 엔진의 정식 발견과 내용이 겹칠 때가 잦다.

**이것을 `engine_count`에 넣지 않는다.** 그 엔진은 "이건 발견 미만"이라고 스스로 판단한 것이고, 그 판단을 뒤집어 교차확인으로 세면 숫자가 부풀어 "여러 엔진이 심각하게 봤다"는 거짓 신호가 된다.

대신 **발견에 `soft_agreement` 주석을 달고 리포트 본문에 한 줄로 적는다** — "다른 관점도 같은 지점을 낮은 강도로 언급함". 계수는 정직하게 유지되고 정보는 안 버려진다.

소프트 항목이 발견과 **같은 방향이 아닐 때**가 있다. 세 갈래로 나눈다:

| 관계 | 처리 |
|---|---|
| **동의** — 같은 지점을 같은 방향으로 언급 | `soft_agreement` 주석 |
| **반대** — 발견이 문제라고 한 동작을 오히려 **고정하자**고 제안 | 주석으로 붙이지 **않는다**. 붙이면 "낮은 강도로 동의함"으로 읽혀 정반대 뜻이 된다. 접힌 "낮은 강도의 언급" 섹션에 사유와 함께 따로 적는다 |
| **모순 항목의 한쪽 편** — 결정 필요 항목의 두 처방 중 하나를 지지 | 그 처방 칸 안에 **맥락으로만** 적는다. 발견 수준의 주석으로 올리면 한쪽에 무게가 실려 "고르지 않는다"는 원칙이 깨진다 |

붙일 발견이 없는 소프트 항목은 접힌 "낮은 강도의 언급" 섹션으로 간다(SKILL.md Phase 7).

### 한 엔진이 검토 후 기각한 항목

한 엔진이 어떤 지점을 **명시적으로 검토하고 문제없다고 판단**했는데 다른 엔진이 발견으로 낸 경우, 자동으로 어느 쪽도 이기지 않는다. 다음을 확인한다:

1. **두 엔진이 같은 질문을 던졌는가** — 기각한 쪽이 답한 질문과 발견한 쪽이 던진 질문이 다르면, 기각은 그 발견을 반박하지 못한다
2. 같은 질문이었다면 **근거가 더 구체적인 쪽**을 택하고, 진 쪽의 판단을 리포트에 함께 적는다

기각 사유는 **그 발견 바로 아래 한 줄**로 붙인다(별도 섹션을 만들지 않는다) — 읽는 사람이 "이건 다른 관점이 이미 봤는데 왜 살아 있지?"를 그 자리에서 알 수 있어야 한다. 접힌 항목이면 접힌 섹션의 해당 행에 붙인다.

> 실제 사례: 한 엔진은 README 표의 숫자가 "기존 설계 문서의 목표치와 일치하는가"를 물어 문제없다고 기각했고, 다른 엔진은 "그 표가 지금 플래그를 켜려는 운영자에게 현재 동작을 오해시키는가"를 물어 발견으로 냈다. 질문이 다르므로 기각이 발견을 무효화하지 않는다 — 발견을 유지하고 기각 사유를 함께 적었다.

## 억제 규칙

**첫 행이 나머지 전부를 뒤엎는 우선 규칙이다** — "순서대로 적용"이라는 말이 "위에서부터 하나씩"으로 읽히면, 아래쪽의 `confidence <= 25` 행이 등급을 안 가리고 먼저 발화해 P0/P1을 검증 게이트에 닿기도 전에 지울 수 있다(실측 지적: confidence 25짜리 P0은 스키마상 정당한 조합인데도 이 순서 오류로 조용히 사라졌다). 그래서 등급 예외를 **가장 먼저** 검사한다 — 아래의 다른 어떤 행도 P0/P1에는 적용되지 않는다.

| 조건 | 처리 |
|------|------|
| `severity in (P0, P1)` | **아래의 폐기·접기 행은 건너뛴다.** 확신도가 아무리 낮아도 자동 폐기·억제하지 않는다. 의심스러우면 Phase 6 검증으로 보낸다. **`pre_existing` 행은 예외** — 등급과 무관하게 다음 행을 그대로 적용한다 |
| `pre_existing: true` | 등급 무관하게 적용. 인라인 코멘트에서 제외. 리포트의 접힌 별도 섹션으로(폐기 아님 — P0/P1 pre_existing도 이 섹션에 남는다) |
| `severity in (P2, P3)` + `confidence <= 25` | 폐기. 엔진 자신이 검증하지 못했다고 말한 것 |
| `engine_count == 1` + `severity in (P2, P3)` + `confidence < 75` | 폐기. 리포트 접힌 섹션에 "억제됨"으로 기록 |
| `engine_count == 1` + `severity == P3` + `covering_engines >= 3` + **아래 면제에 해당하지 않음** | **접는다** (폐기 아님). 인라인 코멘트에서 빼고 리포트 접힌 섹션으로 |

**접기 면제 — 다음 중 하나라도 해당하면 접지 않는다:**

| 면제 조건 | 왜 |
|---|---|
| P0·P1 발견에 **유발 요인으로 연결**된 항목 | 승격 예외 규칙이 "자신은 피해를 안 내지만 다른 발견의 발생 확률을 높이는 것"을 원 등급 유지 + 연결로 처리한다. 그렇게 살려 둔 항목을 접기 규칙이 도로 숨기면 **P0으로 사람을 밀어 넣는 바로 그 안내를 지운다** |
| `soft_agreement`가 붙은 항목 | 다른 엔진이 낮은 강도로 같은 지점을 언급했다면 "한 곳만 집었다"가 사실이 아니다. 계수는 정직하게 1로 두되, 접기 판단에서는 그 언급을 근거로 살린다 |
| 다른 엔진이 **검토 후 기각**했으나 질문이 달라 유지된 항목 | 안 집은 엔진이 취향으로 넘긴 게 아니라 다른 질문에 답한 것이다. 접기 규칙의 전제("대체로 취향 문제")가 성립하지 않는다 |

**단독 지적 P2는 접지 않는다 — 의도된 것이다.** 접기 규칙의 근거("여럿이 읽고 하나만 집었으면 대체로 취향")는 P2에도 논리적으로 적용되지만, P2는 "수정 권장" 등급이라 취향과 실제 결함이 섞이는 구간이다. 여기서 자동으로 접으면 진짜 결함이 접힌 섹션에 묻힌다. 단독 지적 P2가 많아 리포트가 길어지는 것은 받아들인다 — 배지(`⚠️ 단독 지적`)가 이미 읽는 사람에게 신뢰도를 알려 준다.

**다섯 번째 행이 필요한 이유 — 확신도만으로는 노이즈가 안 걸러진다.** 렌즈에 넘기는 프롬프트가 "75 이상으로 매기려면 원문 코드 줄을 인용하라, 못 하면 50으로 내려라"를 강제하므로, 인용할 수 있는 것만 올라와 **결과가 거의 전부 정확히 75로 온다.** 그러면 `confidence < 75` 조건은 실질적으로 아무것도 거르지 못하고, 단독 지적 P3가 리포트의 절반을 차지한다.

그래서 확신도 대신 **"여럿이 봤는데 하나만 언급했다"**를 신호로 쓴다. 세 엔진 이상이 그 파일을 읽고도 한 곳만 P3로 집었다면 대체로 취향 문제다. **폐기가 아니라 접는 이유**는 그 판단이 확신도 기반 폐기만큼 단단하지 않아서다 — 읽고 싶은 사람은 펼쳐 볼 수 있어야 한다.

마지막 줄이 규칙 전체의 안전장치다. 크리티컬한데 확신이 낮은 발견을 조용히 지우는 것이, 오탐 하나를 사람에게 보여주는 것보다 훨씬 비싸다. P0/P1을 내리는 유일한 경로는 Phase 6의 독립 재검증(SKILL.md의 2표 판정표 — `REFUTED` 2/2, 또는 의견이 갈려 강등되는 경우)이며, 그때도 리포트에 흔적을 남긴다.

## 배지

리포트와 코멘트에 붙일 표시.

| 조건 | 터미널 리포트 | PR 코멘트 |
|------|--------------|-----------|
| `engine_count >= 2` | `✅ 교차확인 {n}개 엔진: {엔진명 목록}` | `✅ 독립 리뷰 {n}건이 같은 지적` |
| `engine_count == 1`, `covering_engines >= 2` | `⚠️ 단독 지적: {엔진명}` | `⚠️ 리뷰 {n}건 중 1건만 지적` |
| `covering_engines == 1` | 배지 없음 | 배지 없음 |
| Phase 6에서 강등됨 | `⬇️ 검증 결과 강등 (원래 {등급})` | `⬇️ 추가 검증에서 근거가 약함` |

**PR 코멘트 쪽에 엔진 이름을 쓰지 않는다.** PR 코멘트는 팀원이 읽는 문서다. 엔진 이름·프로파일 이름·내부 워크플로 용어가 나오면 읽는 사람에게는 해독 불가능한 라벨이고, 교차확인이라는 정보만 개수로 전달하면 충분하다. 터미널 리포트는 사용자가 동작을 확인하는 화면이므로 엔진 이름을 그대로 쓴다.

## 리포트 정렬

1. 등급 내림차순 (P0 → P3)
2. 같은 등급이면 `engine_count` 내림차순 — 교차확인된 것이 위로
3. 같으면 `confidence` 내림차순
4. 같으면 파일 경로 알파벳순
5. 같으면 라인 번호 오름차순

이 순서면 "가장 심각하고 가장 여러 엔진이 동의한 것"이 맨 위에 온다. 5단계가 있어야 같은 파일의 두 발견이 매번 같은 순서로 나온다 — 4단계까지만 두면 순서가 실행마다 흔들려 안정 번호(`#`)를 신뢰할 수 없다.
