# Harness Engineering Reference

최종 검증일: 2026-08-27 (아래 각 references/*.md 끝의 "출처" 목록 URL 기준)

## 이 스킬의 역할

스킬·에이전트를 "만드는 절차"는 skill-creator·writing-skills 같은 절차 스킬이 담당한다.
이 스킬은 그 절차 위에서 **무엇을, 어디에, 언제 담고, 어떻게 유지하는지의 판단 기준**을 제공한다.
근거는 Anthropic 공식 문서(code.claude.com/docs) + 통제 실험 + 실무 사례이며, 출처는 각
references 파일 끝에 있다. 절차 스킬과 함께 쓰일 때는 절차는 그 스킬을 따르되, 내용·배치
판단에는 이 기준을 적용한다.

## 핵심 원칙: 기본은 "넣지 않는다"

컨텍스트 파일은 채운다고 성능이 오르지 않는다. 이 질문에 대한 유일한 통제 실험
(ETH Zurich/LogicStar, arXiv 2602.11988)에서 컨텍스트 파일 제공은 과제 성공률을 안정적으로
올리지 못했고(LLM 생성 −0.5~−2%p, 개발자 작성 +2.4%p로 통계적 유의 없음 p=0.21) 추론
비용만 평균 20% 이상 늘었다. 가치가 확인된 것은 **저장소에서 유추 불가능한 정보**뿐이다.

그래서 새 항목은 저마다 "자리 값어치"를 증명해야 한다. 판단 필터는 세 가지 모두 충족:

1. **코드로 유추 불가** — 에이전트가 코드·의존성·디렉토리를 읽어 알 수 있는 것은 넣지 않는다
   (디렉토리 트리, 의존성 목록, 기술스택 개요, 표준 관례).
2. **넓게 적용** — 한 작업에만 필요한 것은 프롬프트에 쓴다.
3. **오래 유효** — 자주 바뀌는 정보는 쓰이기도 전에 낡는다.

## 추가 신호: 관측된 마찰에만 반응한다

커밋마다 "문서화할까?"를 묻지 않는다. 다음 신호가 **실제로 관측될 때만** 추가한다:

1. Claude가 같은 실수를 **두 번째**로 했을 때
2. 코드 리뷰가 "Claude가 이 코드베이스에 대해 알았어야 할" 것을 잡았을 때
3. 지난 세션에 쳤던 교정·설명을 또 입력하게 될 때
4. 신규 팀원이 똑같이 필요로 할 맥락일 때

"같은 실수 두 번"은 그 항목이 실제 실패를 막는다는 증명이다 — 이것이 위 실험이 말한
"유용한 항목"의 조건과 일치한다.

## 배치 결정 트리

추가하기로 했다면, 위에서부터 처음 걸리는 자리에 둔다. 원칙: **상시 로딩은 최소로,
나머지는 온디맨드로, 반드시 지킬 것은 강제 계층으로.**

```
그 지시는...
│
├─ 예외 없이 매번 반드시 실행/차단돼야 하나? (린트, 위험 명령 차단)
│   └─ YES → Hook·CI  (산문 지시는 권고일 뿐, 훅은 결정적으로 강제)
│
├─ 클라이언트가 강제할 설정인가? (도구 허용/차단, 권한 모드)
│   └─ YES → settings.json의 permissions  (컨텍스트에 실리지 않음)
│
├─ 외부 시스템의 실시간 데이터·행위인가? (이슈 트래커, 로그, DB)
│   └─ YES → MCP  (단, CLI로 대체 가능하면 CLI 우선 — 도구 정의도 컨텍스트 비용)
│
├─ 여러 단계 절차이거나 가끔만 필요한 도메인 지식인가?
│   └─ YES → Skill  (description만 상시, 본문은 호출 시 로드)
│
├─ 특정 경로·파일유형에만 적용되나?
│   └─ YES → .claude/rules/<주제>.md + paths: 글롭  (매칭 파일 읽을 때만 로드)
│
├─ 매 대화 필요한, 코드로 유추 불가한 사실·규약인가?
│   └─ YES → CLAUDE.md. 어느 CLAUDE.md인가?
│       ├─ 저장소 전체·모든 작업에 적용되나? → 루트 CLAUDE.md
│       └─ 특정 패키지·디렉토리 작업에만 적용되나? → 그 디렉토리의 CLAUDE.md
│           (그 폴더 파일을 읽을 때만 온디맨드 로드된다 — 담당자 없으면 방치되기 쉽다)
│
└─ 어디에도 해당 없음 → 넣지 않는다
```

스코프 선택: 팀의 공통 동작을 결정하는 것만 프로젝트 스코프(git 커밋·PR 리뷰), 개인
취향·실험은 개인 스코프(`~/.claude/`, `*.local.*`). 같은 이름이 양쪽에 있을 때 이기는
쪽은 요소마다 다르다 — references/loading-and-cost.md의 우선순위 표 참조.

## 사용 흐름 — 판단하고 제안하되, 반영은 합의 후에

하니스 파일 대부분(CLAUDE.md·rules·팀 skill)은 git으로 공유되는 팀 설정이다. 판단이
끝났다고 바로 파일을 고치지 않는다 — 판단 근거와 제안을 먼저 사용자에게 제시하고,
**합의된 방향으로만** 실제 반영(Edit/Write)에 들어간다.

1. **판단** — 사용자가 반영하려는 내용에 위 결정 트리를 적용해 후보 위치를 정한다.
2. **제안** — 판단 결과만 던지지 말고, 다음 형식으로 근거·초안까지 갖춰 제시한다:

   ```
   ## 제안: <내용 한 줄 요약>

   **위치**: <CLAUDE.md(루트) | CLAUDE.md(하위 디렉토리 경로) | .claude/rules/<파일>.md | Skill>
   **근거**: <결정 트리의 어느 분기에 해당하는지 — 예: "src/api/** 에만 적용되므로
             rules + paths: 글롭. 루트 CLAUDE.md에 넣으면 무관한 작업에도 상시 로드됨">
   **제안 문구**: <실제로 넣을 문장·섹션 초안>
   **대안**(있다면): <다른 후보와 그걸 배제한 이유>
   ```

3. **합의** — 사용자가 제안을 받아들이거나 다른 위치·문구를 제시하면 그에 맞춰 조정한다.
   후보가 팽팽하면(예: rules vs 하위 CLAUDE.md) AskUserQuestion으로 선택지를 명확히
   제시해도 좋다.
4. **반영** — 합의된 위치·문구로 실제 파일을 Edit/Write한다.

판단·제안 단계에서 대화를 끝내지 않는다(근거 없이 "어디에 넣을까요?"만 던지지 않는다).
동시에 합의 없이 곧장 파일부터 고치지도 않는다 — 이 두 가지가 이 흐름의 핵심이다.

## 검증과 유지: 추가한 뒤의 의무

항목은 에이전트의 행동을 실제로 바꿔야만 정당하다.

- **행동 검증**: 추가 후 그 오류의 재발이 줄었는지 관측한다. 지시 없이도 Claude가 잘하면
  삭제하거나 훅으로 바꾼다.
- **크기**: CLAUDE.md는 파일당 200줄 미만 목표(공식 memory 문서). 길수록 컨텍스트를 먹고
  지시 준수율이 떨어진다. 초과하면 섹션을 분류해 Skill·references로 이관하고 **원본에서
  삭제**한다 — 옮기고 안 지우는 중복이 가장 흔한 실수다.
- **가지치기 시점**: ① 주요 모델 릴리스 후(옛 모델 우회 규칙은 새 모델엔 오버헤드) ② 정기
  감사(분기 1회 권장, 공식 블로그는 3~6개월) ③ `/doctor`가 코드로 유추 가능한 내용의 트림을
  제안한다(v2.1.206+).
- **소유와 리뷰**: 루트 하니스 파일은 전담 팀 또는 책임자(DRI)를 정한다. 하니스 파일 변경은
  그것을 유발한 코드와 **같은 PR**에서 코드처럼 리뷰한다 — 규약이 코드를 따라가게 하고,
  틀린 지시가 매 세션 권위 있게 반복되는 것(baked-in)을 막는다.
- **측정**: 스킬 사용은 OpenTelemetry로 추적한다 — `OTEL_LOG_TOOL_DETAILS=1`을 켜면
  `tool_result` 이벤트의 `skill_name`과 비용 카운터의 `skill.name` 속성이 기록된다.
  안 쓰이는 스킬은 통합·폐기한다.
- **이 스킬 자체의 재검증**: 위 최종 검증일 이후 오래됐거나(주요 모델 릴리스 후 등)
  버전 번호·우선순위 표·환경변수명처럼 Claude Code 특정 메커니즘에 의존하는 판단이라
  못 미더우면, claude-code-guide 에이전트에게 그냥 "확인해줘"라고 시키지 말고 해당
  references/*.md 끝의 "출처" URL을 직접 짚어서 재확인시킨다. 근거: URL 없이 일반
  검색을 시키면 에이전트가 다른 페이지를 열어 "확인 불가"라는 거짓 불확실 신호를 낼 수
  있다(실측: 같은 사실을 URL 없이 물었을 때 4개 항목이 "확인 불가"로 나왔으나, 정확한
  URL을 짚어 다시 물으니 전부 원문 그대로 확인됨). 일반 소프트웨어 공학 원칙(ADR,
  docs-as-code 등)은 잘 안 바뀌므로 재검증 대상에서 제외한다.
