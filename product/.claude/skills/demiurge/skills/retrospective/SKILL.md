# Retrospective Skill

## Overview

AI와 협업한 세션을 회고하여 교훈(Lessons & Learned)을 뽑아내고, AI 하니스(Skills, CLAUDE.md, Memory, Hooks 등)에 반영하는 프로토콜입니다.

**역할 분담**: 이 스킬은 "이번 세션에서 무엇을 배웠나"를 찾고, 반영 범위를 정하고, 승인을 받는 절차를 맡는다. "그 교훈을 어디에 어떻게 넣을지"의 판단 기준(넣지 않는다 필터, 배치 결정 트리, 스코프, 공식 문서 대조)은 `demiurge:harness-engineering` 스킬이 가진다. 같은 기준을 이 스킬에 다시 적지 않는다.

**철학**: Compound Engineering의 "Each unit of work should make subsequent units easier"를 AI 협업 전체에 적용. 코드 문제뿐 아니라 모든 AI 협업 경험에서 교훈을 추출하여 하니스를 발전시킨다.

```
┌───────────────────────────────────────────────────────────────┐
│              Retrospective Protocol (4-Phase)                  │
├───────────────────────────────────────────────────────────────┤
│  Phase 1: 교훈 추출 + 우선순위                                 │
│    세션 신호 6가지 분석 + 변경 파일 확인 + 사용자 인터뷰(평문)   │
│    → L{N} 포맷으로 구조화, 우선순위 부여                        │
│                        │                                       │
│  Phase 2: 교훈마다 harness-engineering 흐름 적용               │
│    공식 문서 대조 → 넣지 않는다 필터 → 위치 판단 → 제안 문구     │
│                        │                                       │
│  Phase 3: 사용자 승인                                         │
│    모든 교훈의 제안을 한 표로 보여 주고 평문으로 승인 받기       │
│                        │                                       │
│  Phase 4: 반영                                                │
│    승인된 것만 반영 → 결과 요약                                 │
└───────────────────────────────────────────────────────────────┘
```

## When to Use

- AI가 같은 유형의 실수를 반복할 때
- 세션에서 많은 교정/거부가 발생했을 때
- 스킬을 실행했는데 결과물이 기대와 달랐을 때
- AI 하니스(Skills, CLAUDE.md, Hooks 등)를 개선하고 싶을 때
- 세션이 길어져서 배운 것을 정리하고 싶을 때

**사용하지 않을 때:**
- 단순 질문/답변 세션 (교훈이 없음)
- 이미 /retrospective를 실행한 직후 (중복)

**참조 스킬**: `demiurge:harness-engineering`(Phase 2 배치 판단), `update-config`(Phase 4 Hooks 반영)

## Phase 1: 교훈 추출 + 우선순위

### Step 1-1: 세션 컨텍스트 자동 분석

현재 대화 컨텍스트에서 다음 **6가지 신호**를 식별:

| 신호 | 설명 | 예시 |
|------|------|------|
| **AI 실행 실패** | AI가 도구 실행 중 에러를 낸 지점 | Write 도구가 "File has not been read yet" 에러 |
| **사용자 교정/거부 (도구)** | 사용자가 도구 호출을 거부하거나 교정한 경우 | 도구 호출 거부 후 피드백 |
| **사용자 교정/거부 (제안)** | AI의 텍스트/내용 제안을 사용자가 수정한 경우 | "확보 -> 높였습니다"로 대안 제시 |
| **재시도/방향 전환** | AI가 접근 방식을 바꾼 지점 | subagent -> 현재 컨텍스트로 전환 |
| **반복 질문/요청 패턴** | 사용자가 반복적으로 같은 유형의 요청을 한 경우 | "이건 왜 빠졌어?" 반복 = AI가 선제적으로 체크해야 함 |
| **누락 지적** | 사용자가 "이것도 해줘", "왜 안 했어?" 등으로 누락을 지적 | "Experience Summary가 왜 없어?" |

### Step 1-2: 변경 파일 분석

```bash
git diff --name-only HEAD~{N}  # 이 세션에서 변경된 파일 목록
```

변경된 파일 중 하니스 관련 파일(Skills, CLAUDE.md, settings.json, memory/)이 있으면, 어떤 변경이 왜 이루어졌는지를 교훈과 연결.

### Step 1-3: 사용자 인터뷰

다음 3가지를 한 메시지에 평문으로 묻는다:

1. "이 세션에서 AI가 잘못하거나 불편했던 점이 있나요?"
2. "다음 세션에서 AI가 기억했으면 하는 것이 있나요?"
3. "이 세션에서 발견한 패턴이나 규칙이 있나요?"

### Step 1-4: 교훈 구조화

각 교훈은 다음 **L{N} 포맷**으로 작성:

```markdown
### L{N}. {짧은 제목}

- **발견 소스**: 실행 실패 / 사용자 교정(도구) / 사용자 교정(제안) / 방향 전환 / 반복 패턴 / 누락 지적 / 사용자 인터뷰
- **문제**: 무엇이 잘못되었는가 (구체적 사례)
- **우선순위**: 높음 / 중간 / 낮음
```

### Step 1-5: 우선순위 판단

- **높음**: 같은 실수가 반복될 가능성이 높고, 반영하면 즉시 효과가 있는 것
- **중간**: 개선하면 좋지만 급하지 않은 것
- **낮음**: 특수한 상황에서만 발생하는 것

**Exit Criteria**: 교훈이 1개 이상 추출되고, 모두 우선순위가 할당됨.

---

## Phase 2: 교훈마다 harness-engineering 흐름 적용

교훈마다 `demiurge:harness-engineering` 스킬의 사용 흐름으로 반영 위치와 문구를 정한다. 이 단계에서는 파일을 고치지 않는다(반영은 Phase 4).

1. **공식 문서 대조**: 바뀌는 하니스 요소와 관련된 공식 문서를 확인한다(확인 빈도·도구·실패 처리는 harness-engineering의 references/doc-check.md).
2. **넣지 않는다 필터**: 코드로 유추 가능하거나, 한 작업에만 필요하거나, 금방 낡는 교훈은 넣지 않는다. 넣지 않기로 한 교훈은 그 이유를 Phase 3 표에 남긴다.
3. **위치 판단**: 배치 결정 트리(memory, Hook, settings, MCP, Skill, rules, CLAUDE.md, CLAUDE.local.md)와 스코프 기준으로 위치를 정한다.
4. **제안 문구**: 실제로 넣을 문장과 근거를 harness-engineering의 제안 형식으로 적는다.

교훈끼리 충돌하면(같은 위치에 반대 규칙 등) 충돌 사실을 Phase 3 표에 표시한다.

**Exit Criteria**: 모든 교훈에 "반영 위치 + 제안 문구" 또는 "넣지 않음 + 이유"가 정해짐.

---

## Phase 3: 사용자 승인

Phase 2의 결과를 한 표로 보여 주고, 같은 메시지 끝에 평문으로 승인 범위를 묻는다.

```markdown
| # | 교훈 | 우선순위 | 반영 위치 | 제안 문구(요약) |
|---|------|---------|----------|----------------|
| 1 | ... | 높음 | skills/xxx/SKILL.md | ... |
| 2 | ... | 높음 | memory/feedback_xxx.md | ... |
| 3 | ... | 낮음 | 넣지 않음 | (이유) |
```

승인 방식은 세 가지다:

1. **전체 승인**: 모든 제안을 반영
2. **일부만 승인**: 반영할 번호를 고름 (예: "1, 3만 반영")
3. **수정 후 승인**: 특정 교훈의 위치·문구를 고친 뒤 반영

충돌로 표시된 교훈은 사용자가 어느 쪽을 택할지 정한 뒤에 반영한다.

**Exit Criteria**: 사용자가 반영할 교훈 목록을 확정함.

---

## Phase 4: 반영

승인된 제안만 반영한다.

- **Memory**: memory/ 파일을 만들거나 고친 뒤 MEMORY.md 인덱스에 한 줄을 추가한다.
- **Hooks**: settings.json을 직접 고치지 않고 `update-config` 스킬을 Skill 도구로 호출한다.
- **그 밖의 하니스 파일**: Phase 2에서 정한 위치에 반영한다.
- **범위 판별**: 프로젝트 한정 규칙은 그 레포의 `.claude/`에 반영한다. 전역 규칙·스킬·에이전트의 위치와 배포 절차는 사용자 전역 지침에 정해진 것을 따르고, 정해진 것이 없으면 `~/.claude/`에 직접 쓰지 말고 사용자에게 묻는다.

### 반영 결과 요약

모든 반영 완료 후 결과 테이블을 출력:

```markdown
## Retrospective 결과

| # | 교훈 | 반영 위치 | 반영 상태 |
|---|------|----------|----------|
| 1 | ... | skills/xxx/SKILL.md | 반영됨 (SKILL.md:L45) |
| 2 | ... | memory/feedback_xxx.md | 반영됨 |
| 3 | ... | 넣지 않음 | 이유: ... |

총 N개 교훈 중 M개 반영 완료.
```

**Exit Criteria**: 승인된 모든 교훈이 대상 파일에 반영됨 + 반영 결과 요약 테이블 출력.

## 제약사항

- 한 세션에서 추출하는 교훈은 실행 가능한 수준으로 제한 (너무 추상적인 교훈은 구체화하거나 제외)

---

## Common Mistakes

- 교훈이 너무 추상적 ("더 잘해야 한다") → 구체적 사례와 변경 제안이 있어야 함
- 모든 교훈을 어딘가에 넣으려 함 → harness-engineering의 "넣지 않는다" 필터를 먼저 통과시킬 것
- 교훈 간 충돌을 무시하고 반영 → 사용자에게 먼저 확인
