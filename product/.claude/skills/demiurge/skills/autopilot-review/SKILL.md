# Autopilot Review — 리뷰→수정을 수렴할 때까지 자율 반복

<!-- model intentionally omitted — 회차마다 review-ensemble·리뷰어 Agent를 chain 호출하므로 세션 모델을 상속한다 (rules/skills.md §1) -->

한 번의 리뷰는 한 번의 스냅샷이다. 이 스킬은 **리뷰 → 수정 → 다시 리뷰**를 사람 없이 돌리되,
"발견 0건"이 아니라 **"동작을 바꾸는 발견이 더 없음"**에서 멈추고, 왜 여러 번 돌아야 했는지를
사람이 읽을 보고서와 기억으로 남긴다.

```
  회차 N
  ┌──────────────┐  발견   ┌──────────────┐  수정   ┌──────────────┐
  │ (1) 리뷰 앙상블│───────>│ (2) 판정·검증  │───────>│ (3) 수정+시험  │
  └──────────────┘         └──────────────┘         └──────┬───────┘
         ▲                                                  │ 커밋
         │        (5) 수렴 판정 — 아니면 회차 N+1          │
         └──────────────── (4) 전체 검증 <─────────────────┘
                                   │ 수렴
                                   ▼
                         (6) 보고서 + 학습 저장
```

**핵심 전제 — 회차마다 앞 회차의 수정이 새 결함을 만든다.** 실측(6회차 반복)에서 2차는 1차 수정의
회귀, 3차는 2차가 막은 곳을 다른 문으로 다시 연 것, 4차는 3차의 절반짜리 방어, 5차는 4차가 없앤
버튼을 가리키던 문구였다. 그래서 이 스킬의 리뷰 회차는 "전체를 다시 훑기"가 아니라
**"방금 고친 자리를 최우선으로 다시 보기"**다.

## 언제 쓰나

- 구현이 끝난 브랜치를 사람 없이 리뷰·수정·재검증까지 끝내고 싶을 때
- `/review-ensemble`이나 `/code-review`가 낸 발견을 고치고 나서 "고친 것이 또 문제를 만들지 않았는지"까지 확인하고 싶을 때
- `/goal`과 함께 "문제가 안 나올 때까지"를 조건으로 자율 완주시킬 때

쓰지 않는 경우: 리포트만 원할 때(`/review-ensemble`), 계획서를 구현할 때(`/autopilot`), 수정 하나를 디버깅할 때(`/debug`).

## 인자

| 토큰 | 뜻 | 기본 |
|---|---|---|
| `quick` / `standard` / `deep` | review-ensemble 프로파일 | `deep` |
| `--max-rounds N` | 회차 상한. 수렴하지 않아도 여기서 멈추고 보고한다 | 8 |
| `--no-commit` | 회차별 커밋을 하지 않고 워킹트리에만 남긴다 | 커밋함 |
| `base:<ref>` | 비교 기준 | 기본 브랜치와의 merge-base |

엔진은 review-ensemble의 [engines.md](../review-ensemble/engines.md)를 그대로 따른다.
Codex 교차 검증을 포함한 **모든 엔진을 쓴다** — 사용자가 특정 엔진을 빼라고 하지 않는 한 제외하지 않는다.

## Phase 0 — 진입과 기준선

1. 사용자에게 묻지 않는다. 이 스킬은 자율주행이 전제이므로, 갈림길은 판단 후 보고서에 적는다. 멈춰야 하는 경우(기준선 빨간불, 발견이 두 회차 연속 증가)에도 질문 대신 **상황과 권고를 출력하고 종료**한다.
2. 기준 브랜치·merge-base를 구한다. **원격이 없어도 멈추지 않는다** — `gh repo view`가 실패하면 로컬 `main`/`master`로 대체하고 그 사실을 보고서에 적는다.
3. 작업 트리가 깨끗한지 확인한다. 미커밋 변경이 있으면 **그 상태로 시작하되** 보고서에 적는다 — 회차 커밋이 사용자 변경과 섞이므로 `--no-commit`을 권한다.
4. **기준선 검증을 먼저 돌린다** — 프로젝트의 시험·타입·린트·빌드 명령 전부. 여기서 이미 빨간불이면 리뷰가 아니라 수정부터 해야 하므로 멈추고 알린다. 통과했으면 그 명령 묶음을 `VERIFY`로 기억한다(회차마다 똑같이 돌린다).
5. 라운드 작업 폴더 `<repo>/.autopilot-review/round-N/`를 만든다. 리뷰어 산출물·맥락 파일이 여기 쌓인다. 저장소에 올리지 않도록 `.git/info/exclude`에 넣는다.
6. 프로젝트에 **"고치지 않기로 한 것" 목록**이 이미 있으면(설계 문서의 보류 표, `docs/solutions/` 등) 찾아 둔다. 없으면 회차 1이 끝날 때 만든다.

## Phase 1 — 회차 N 리뷰

**회차 1**: `Skill(review-ensemble, "<프로파일> base:<merge-base>")`를 그대로 부른다. 로컬 모드 절차·엔진 선택·병합·P0/P1 반박 검증까지 그 스킬이 다 한다.

**회차 2 이후**: review-ensemble의 엔진 목록은 같게 쓰되, 모든 리뷰어 프롬프트 앞에 **회차 맥락 파일**을 붙인다. 맥락 파일 양식은 [references/round-context.md](references/round-context.md)에 있다. 담기는 것:

- 전체 diff **와 별도로** "이번 회차에 바뀐 부분" diff — 회귀 위험이 가장 높은 곳이라고 명시
- 앞 회차에서 고친 것 목록(무엇을 왜)
- **이미 판단이 끝나 다시 올릴 필요가 없는 것** 목록 — 근거가 기록된 곳을 가리킨다. 다만 "새 실패 시나리오가 있으면 그때는 올려도 된다"는 여지를 남긴다
- 후반 회차(발견의 성격이 얕아진 뒤)에는 **"findings가 빈 배열인 것이 값진 답이다 — 억지로 채우지 마라"**를 명시하고 확신도 75 미만을 막는다. 이것이 없으면 억지로 채운 P3가 수렴 판단을 흐린다

회차 2 이후에도 P0/P1 단독 지적은 review-ensemble Phase 6 방식(서로 다른 모델 2표)으로 검증한다.

**리뷰어에게 반드시 붙이는 지시 두 줄** — 시험 렌즈가 변형 실험을 하면서 추적 파일을 직접 고쳐, 같은 트리를 보던 다른 리뷰어들이 중간 상태를 보고 오탐을 낸 일이 있었다:
- 변형 실험은 **격리 사본에서만**, 끝나면 `git status --porcelain`이 빈지 확인할 것
- 파일을 수정하지 말 것, GitHub에 게시하지 말 것

내장 `code-review`를 로컬 모드로 부를 때 upstream이 없으면 빈 diff를 본다. 부르기 직전 `git branch --set-upstream-to=<base>`로 잠시 잡아 주고, 회차가 끝나면 `--unset-upstream`으로 되돌린다.

리뷰어는 백그라운드 Agent다. 산출물 폴더를 폴링하되 **한 번의 대기는 10분을 넘기지 않는다**(도구 시간 상한). 도착한 결과는 도착하는 대로 사실 확인에 들어간다 — 전부 모이길 기다리지 않는다.

## Phase 2 — 판정과 사실 확인

발견을 받으면 코드를 열어 **직접 확인한 뒤** 고친다. 리뷰어가 "실험으로 확인했다"고 해도 인용된 줄이 실제로 그 파일 그 자리에 있는지, 주장한 전제가 레포 안에서 성립하는지를 본다. 이 확인에서 갈리는 것들:

| 판정 | 처리 |
|---|---|
| 사실이고 동작을 바꾼다 | 이번 회차에 고친다 |
| 사실이지만 전제를 레포 안에서 확인할 수 없다 (예: 외부 API가 429를 언제 주는지) | 고치지 않고 **보류 표**에 근거와 함께 적는다. 확인 방법도 적는다 |
| 사실이지만 지금 규모에 맞지 않는 처방 | 보류 표에 적는다 |
| 이미 보류 표에 있고 새 시나리오가 없다 | 무시. 다음 회차 맥락의 "판단 끝난 목록"에 그대로 둔다 |
| 리뷰어가 서로 반대 처방을 낸다 | 하나를 고르고 그 이유를 보류 표나 커밋 메시지에 적는다 |

보류 표는 프로젝트 문서에 남는다(설계 문서의 "고치지 않은 것" 절 등). **보류 항목은 한 줄에 "왜 지금은 아닌가"가 있어야 한다** — 다음 회차 리뷰어와 다음 사람이 같은 항목을 또 올리지 않게 하는 유일한 장치다.

## Phase 3 — 수정: 고친 자리마다 옛 동작을 잡는 시험

수정 하나를 넣을 때마다 아래를 함께 한다. 0번은 고치기 **전에**, 1~3번은 고치면서.

0. **감쌀 대상과 물려받은 값을 먼저 확인한다.** 관용구를 옮겨 쓰는 것과 기존 값을 인계받는 것도 사실 주장이다 — **의심이 들지 않아도** 그 대상의 실제 동작과 그 값의 근거를 확인한다. 상한·재시도·취소로 감싸려는 `await`가 정확히 무엇을 기다리는지(그 API의 성공 신호가 헤더인지 본문인지, 연결인지 완료인지), 그리고 내가 유도하지 않은 숫자(기존 상수·인계받은 상한)가 어디서 왔는지를 소스와 문서에서 본다. 실측에서 회귀를 만든 수정은 관용구를 옮기며 `fetch`가 헤더 도착에 이행된다는 것을 확인하지 않았고, 20초 상한은 사용자 인내에서 유도한 값이 아니라 물려받은 5초에 바깥으로 더해 나온 값이었다. "신중하게 판단했다"로는 안 잡힌다 — 판단이 아니라 타이핑이었기 때문이다.
1. **그 수정을 지키는 시험을 넣는다.** 시험 없는 수정은 다음 회차에 회귀로 돌아온다.
2. **옛 동작에서 그 시험이 실제로 실패하는지 확인한다.** 격리 사본에 옛 코드(또는 방어를 뺀 코드)를 넣고 시험을 돌린다. 통과만 보면 아무것도 증명되지 않는다 — 실측에서 "추첨을 통째로 없애도 시험 13개가 전부 통과"가 나왔다. 절차는 [references/mutation-check.md](references/mutation-check.md).
3. **형제 경로를 센다.** 수정은 "막으려는 상태"를 머릿속 한 경로로만 그리기 쉽다. 타임아웃이면 헤더·본문 두 단계, 상한이면 전체·개별 두 층, 유출이면 오류·로그·응답 세 출구, 버튼을 없앴으면 그 버튼을 가리키던 문구. 고치기 전에 형제를 세어 두면 다음 회차의 발견이 절반으로 준다.

시험 자료를 만들 때: 검사가 여러 개면 **온전한 자료를 기준으로 한 항목씩만** 어긋뜨린다. 여러 항목을 한꺼번에 뺀 자료는 먼저 걸리는 검사 하나만 지켜 준다(실측: 검사 5개 중 4개가 미검증). 다른 파일의 상수에 기대는 시험은 값을 **소스에서 직접 읽는다** — 손으로 베낀 숫자는 원본이 바뀌어도 초록불이다.

주석을 고칠 때: 근거가 실제 코드·라이브러리 동작과 맞는지 **소스를 열어 확인한 뒤** 쓴다. 실측에서 주석 정확성 렌즈가 회차마다 최다 발견을 냈고, 대부분이 "코드는 맞는데 이유가 틀린" 경우였다. 같은 사실을 두 곳에 적으면 반드시 어긋나므로 한쪽이 다른 쪽을 가리키게 한다.

## Phase 4 — 검증과 커밋

1. `VERIFY` 전부 실행. 시간 의존 시험이 늘었으면 `-race -count=3`(Go) 같은 반복 실행도 한 번 돌린다.
2. 하나라도 빨간불이면 그 수정을 되돌리고 보류 표에 "고치려다 실패, 사유"로 남긴다. 트리를 빨간 채로 다음 회차에 넘기지 않는다.
3. 프로젝트 문서를 이번 회차 상태에 맞춘다 — 보류 표, 인계 문서의 회차 기록. **수치(시험 개수·파일 수)는 문서에 적지 말고 명령으로 대체한다**; 숫자는 다음 커밋에 낡는다.
4. `--no-commit`이 아니면 회차별로 커밋한다. 메시지는 "무엇을 고쳤는지"보다 **"무엇이 틀려 있었는지"**를 사람 말로 적는다 — 이 커밋이 다음 회차 리뷰어와 다음 사람에게 회차의 기록이다. 기본 브랜치에서는 절대 커밋하지 않는다(브랜치를 먼저 판다).

## Phase 5 — 수렴 판정

회차가 끝날 때마다 회차표에 한 줄을 더한다: 회차 · 발견 수 · 등급 분포 · 성격(사용자가 겪는 결함 / 앞 회차의 회귀 / 진단 흔적 / 시험 사각지대 / 주석·문서) · 대표 발견.

**멈추는 기준은 "발견 0건"이 아니다.** 적대적 리뷰는 계속 돌리면 언제나 무언가(주석의 뉘앙스, 더 조일 수 있는 검사)를 찾아낸다. 판정 기준은 [references/convergence.md](references/convergence.md)에 있고, 요지는:

- **동작을 보는 관점들**(정확성·조용한 실패·적대적)이 한 회차에 **0건**을 냈고,
- 그 회차의 나머지 발견이 전부 주석·시험·문서 정밀도(P3)라서 그 회차 안에 다 반영했으며,
- 회차별 발견 수가 **단조 감소**해 왔다면

→ 수렴. 그 다음 회차는 돌리지 않는다. 대신 **마지막 수정분만 보는 짧은 확인 회차**(렌즈 3~4개, "마지막 수정이 새 문제를 만들었는가"만 묻는다)를 한 번 돌려 끝낸다 — 이것이 없으면 마지막 수정이 검토되지 않은 채 남는다.

`--max-rounds`에 닿았는데 수렴하지 않았으면 멈추고, 마지막 회차의 발견을 그대로 보고서에 싣는다. 수렴한 척하지 않는다.

## Phase 6 — 보고서와 학습

두 가지를 남긴다. 양식은 [references/report.md](references/report.md).

**대화에 내는 보고서** — 사람이 이것만 읽고 무슨 일이 있었는지 알아야 한다:
- 회차표(위 Phase 5의 표)와 총 회차 수
- **왜 여러 번 돌아야 했는가** — 회차별로 "앞 회차의 무엇이 다음 회차의 발견을 만들었는지" 사슬로
- 무엇을 학습했는가 — 이번 반복에서 드러난 코드 작성 습관의 개선점. 일반화해서 쓴다(이 레포에서만 통하는 말이 아니라 다음 레포에서도 쓸 수 있게)
- 코드로 답할 수 없어 사람이 정해야 하는 것(보류 표의 요약)
- 검증 상태와 커밋 목록

**기억에 남기는 것** — 메모리 디렉터리에 `feedback` 타입으로. 이번 반복에서 새로 배운 것만 쓰고, 이미 있는 기억과 겹치면 그 파일을 갱신한다. 실측에서 나온 네 가지가 기본 후보다: 고친 자리 재검토, 방어를 끄고 시험 실패 확인, 수렴 기준, 주석 근거 대조. 이 네 가지가 이미 기억에 있으면 **이번 실행에서 새로 드러난 것만** 더한다.

프로젝트에 `docs/solutions/`가 있으면 `Skill(compound-engineering:ce-compound, "mode:headless ...")`로도 누적한다.

## `/goal`과 함께 쓰기

이 스킬은 회차마다 수십 개의 Agent를 띄우므로 한 턴이 길다. 자율 완주를 보장하려면 사용자에게 이렇게 안내한다:

```
/goal autopilot-review로 <브랜치>를 문제가 더 안 나올 때까지 리뷰·수정 반복
```

`/goal`이 없으면 한 회차를 끝내고 회차표와 "다음 회차를 돌리려면 '계속'"을 출력한 뒤 멈춘다.

## 흔한 핑계 — 이 생각이 들면 멈춰서 의심하라

| 핑계 | 현실 |
|---|---|
| "이 수정은 명백해서 시험 없이 넣어도 된다" | 실측에서 회귀를 만든 수정 전부가 "명백한" 수정이었다. 시험 없는 수정은 다음 회차의 발견이다 |
| "시험이 통과했으니 지켜진다" | 통과는 "지금 코드가 이렇게 한다"의 기록일 뿐이다. 방어를 끄고 실패하는지 봐야 한다 |
| "리뷰어가 실험으로 확인했다니 믿자" | 리뷰어의 인용을 그 파일 그 줄에서 직접 본다. 전제가 레포 밖 일반 지식이면 보류 표행이다 |
| "발견이 0건이 될 때까지 돌리자" | 끝나지 않는다. 기준은 "동작을 바꾸는 발견이 없음"이다 |
| "이 항목은 지난번에 안 고치기로 했으니 무시" | 새 실패 시나리오가 붙었는지 본다. 붙었으면 보류 판단을 뒤집는다 |
| "마지막 수정은 작으니 재검토 생략" | 5차의 발견이 바로 4차의 작은 수정(버튼 제거)이 남긴 문구였다 |
| "수치를 문서에 적어 두면 친절하다" | 숫자는 다음 커밋에 낡아 다음 사람을 오도한다. 명령을 적는다 |
| "리뷰어들이 알아서 격리해서 실험할 것" | 실측에서 추적 파일을 직접 고친 리뷰어 때문에 다른 리뷰어가 P1 오탐을 냈다. 지시를 붙인다 |
