# 변형 확인 — 방어를 끄고 시험이 실패하는지 본다

시험이 통과한다는 것은 "지금 코드가 이렇게 한다"의 기록일 뿐, "무엇을 지키는지"를 보장하지 않는다.
둘의 차이는 코드를 망가뜨려 봐야만 드러난다. 수정 하나마다 아래를 한 번 돌린다.

## 절차

```
1. 격리 사본을 만든다          — 추적 파일을 직접 고치지 않는다 (다른 리뷰어·도구가 같은 트리를 본다)
2. 사본에서 방어를 끈다        — 옛 코드로 되돌리거나, 새로 넣은 조건·검사 한 줄을 지운다
3. 사본에서 그 시험을 돌린다   — 실패해야 한다
4. 사본을 지운다               — git status --porcelain 이 비어 있는지 확인
```

**실패하지 않으면 시험이 아니다.** 그때는 시험을 고쳐서 3번이 실패하게 만든 뒤, 원본에서 통과하는지 다시 본다.

## 격리 사본 만드는 법

같은 패키지·디렉터리 안에 임시 폴더를 만들어 대상 파일과 시험 파일만 복사하면 import 경로가 그대로 통한다.

```bash
# TypeScript(vitest) — lib/pick.ts 를 확인할 때
mkdir -p lib/__mc__ && cp lib/pick.ts lib/pick.test.ts lib/__mc__/
#   lib/__mc__/pick.ts 에 변형을 넣는다 (아래 예)
npx vitest run lib/__mc__/pick.test.ts 2>&1 | grep -E '^ *Tests '
rm -rf lib/__mc__
```

```bash
# Go — 패키지 단위라 사본 대신 원본을 잠깐 고치고 git checkout 으로 되돌리는 편이 간단하다.
# 단, 다른 리뷰어가 같은 트리를 보고 있지 않을 때만. 리뷰 회차 도중이면 scratchpad에 레포를 복사해서 한다.
python3 - <<'PY'
p='internal/kakao/client.go'; s=open(p).read()
s=s.replace('if readErr != nil && (ctx.Err() != nil || errors.Is(readErr, context.DeadlineExceeded)) {',
            'if readErr != nil && ctx.Err() != nil {')      # 4차 이전 조건으로 되돌림
open(p,'w').write(s)
PY
go test ./internal/kakao/ -run 'PerPageTimeout' 2>&1 | grep -E 'FAIL|ok'
git checkout internal/kakao/client.go
```

## 변형의 종류 — 무엇을 끄나

| 수정의 종류 | 끄는 방법 |
|---|---|
| 새 검사·조건을 넣었다 | 그 조건 한 줄을 지운다 (`&& cond` 제거) |
| 순서를 바꿨다 (본문 먼저 만들고 상태 코드 보내기) | 순서를 되돌린다 |
| 상한·타이머를 넣었다 | 상한을 뺀다. **그리고** 값을 터무니없이 작게(1ms) 바꿔도 본다 — "있는지"와 "쓸 만한지"는 다른 시험이다. 값 자체의 출처도 본다 — 사용자 인내(바깥)에서 유도한 값인가, 물려받은 상수에 더해서 나온 값인가. 후자면 시험이 지키는 것은 "어떤 값이든 있다"뿐이다 |
| 무작위·정렬 같은 알고리즘 | 가장 단순한 잘못된 구현으로 바꾼다 (섞기 → 앞에서부터 자르기) |
| 여러 항목을 검사한다 | **항목 하나씩** 지워 본다. 한꺼번에 지우면 하나만 지켜져도 통과한다 |
| 로그·기록을 남겼다 | 대개 시험이 없다. 감출 값(좌표·열쇠)이 있다면 그 값이 문자열에 없는지 보는 시험을 두고, 감추는 코드를 꺼서 확인 |

## 시험 자료를 만드는 규칙

- **온전한 자료 하나를 기준으로 두고 한 항목씩만 어긋뜨린다.** 여러 항목을 동시에 뺀 자료는 먼저 걸리는 검사 하나만 지켜 준다. 실측: 검사 5개를 더했는데 시험 자료가 전부 여러 항목을 동시에 빼는 모양이라, 검사를 하나만 지워도 전 시험이 통과했다.
- **정상 자료 대조군을 함께 둔다.** 검사를 조이다 정상 응답까지 튕겨 내는 회귀를 막는다.
- **다른 파일의 상수는 소스에서 직접 읽는다.** 같은 언어면 이름을 내보내 참조하고, 언어가 다르면 소스를 정규식으로 뽑되 **못 찾으면 실패**하게 한다(못 찾으면 통과하는 대조는 조용히 눈이 먼다). 손으로 베낀 숫자는 원본이 바뀌어도 초록불이다.
- **하한이 있으면 실제 값과 같게 둔다.** "찾은 코드가 7개 이상"이라는 하한에 실제가 8개면, 하나가 사라져도 통과한다.
- **JSON으로 표현 못 하는 값**(Infinity·NaN)은 `JSON.stringify`가 바꿔 버리므로 원문 문자열(`1e999`)로 보낸다.
- 시험 이름이 약속하는 경로를 실제로 밟는지 본다. "본문을 읽다 상한에 걸린다"는 시험이 헤더 단계에서 상한이 터져도 통과한다면, 그 경로에 닿았음을 보이는 단언(오류 문자열의 단계 표시 등)을 더한다.

## 운영 전용 코드

시험이 가짜 서버·가짜 fetch만 쓰면 **운영에서만 부르는 생성자·경로는 커버리지 0**이다. 실측: 생성자가 둘인데 시험은 가짜 서버용만 불러, 운영용에서 상한을 빠뜨려도 초록불이었다(그 상태로 배포하면 모든 조회가 즉시 시간 초과). 생성자·설정 함수는 "값이 채워졌는지"만이라도 직접 시험한다.
